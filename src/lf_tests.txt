Based on your suggestions, I believe lf4 is performing extremely well.

While reviewing my lf_tests.sh script, I realized I had made a silly mistake. My 
chained commands were causing time to capture the "| sort" in addition to lf4, 
find, and fd commands, and as written, the commands invoked "sort" in a 
painfully slow configuration. After putting the sort commands on separate lines, 
the timings changed dramatically. Duh? I also changed the sort commands to 
"LC_ALL=C sort --parallel=7 -S 4G". The sort isn't being timed now, but it, like 
all the file finders is orders of magnitude faster.

All three programs, find, fd, and lf, are astonishingly fast, but lf4, which ran 
in 0.08 seconds is the fastest by a wide margin, 100% faster than fd, which ran 
in 0.16 seconds. 

There are still a couple of things that might make lf4 faster, but the closer it 
gets to perfection, the less I trust my intuition.

For me, using perf and/or strace, with my limited knowledge of them is sketchy 
at best. They seem complicated and have such a wide variety of use cases and 
options, it's difficult to know where to start. I was able to create perf.data 
and strace.out, but I don't know how to interpret them. The perf report is just 
bewildering. I have read (or tried to read) several articles, which I found to 
be confusing. One article by Brendan Gregg, gets off into eBPF and BCC, and 
leading me to believe I need to rebuild my kernel with eBPF support. To tell the 
truth, I find his prose to be circuitous and replete with both elision and 
superfluity. It's hard to put the puzzle together with so many missing pieces 
and extra pieces that don't belong in the picture.

One thing I might try is to accumulate and enqueue batches of task nodes instead 
of one at a time. The task node contains the path to the directory, the depth, 
and optionally the device/inode history, which is only used when the user 
selects the option to check for cyclics.

Another thing I will do, is to add "--parallel=N" to the sort command line, 
using the same number of threads specified on the lf4 command line. I could also 
add "LC_ALL=C", and something like -S 4G depending on available memory. That's 
not really a change to lf4 but it will make the sort much faster.



Guide me.
Keep your current architecture and stop “intuition tuning” until one profile says where time is going.
Separate benchmarks into two phases every run:
traversal only (no sort in timing)
traversal + sort (timed separately)
Build a tiny repeatable benchmark matrix:
-T1, -T2, -T4, -T8 on same tree
record elapsed time, CPU%, minor faults, context switches
this will show whether you are I/O-limited or queue/contention-limited.
Use perf stat first (not perf report) for simple decisions:
if context-switches/migrations spike with threads, reduce contention before adding features
if instructions and branches dominate, optimize per-entry CPU work (path handling, regex path)
Use strace -c to rank syscalls:
if newfstatat/fstatat dominates, reduce metadata calls
if getdents64 dominates with many calls, increase directory read buffer strategy
Use perf top only to find top hot functions, then optimize just the top 1–2.
Defer batching queue nodes unless profiling shows queue hot spots; batching adds complexity and can hurt locality.
Sort tuning is worthwhile, but keep it outside lf4 core:
your LC_ALL=C sort --parallel=N -S ... change is correct for the pipeline stage.
Don’t dig into find source yet; first squeeze wins from your own measured hotspots.
Optional next low-risk win: make cycle-history work fully conditional so normal 
runs avoid that copying/check overhead.
